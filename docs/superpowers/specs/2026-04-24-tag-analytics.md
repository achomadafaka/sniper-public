# Tag Analytics — Market + Wallet-Level Statistics

**Date:** 2026-04-24
**Status:** spec draft, pre-implementation
**Parent:** [wallet-taxonomy-migration](./2026-04-23-wallet-taxonomy-migration.md) (Stage 1–4 shipped)
**Companion:** [v2 execution profile](./2026-04-23-wallet-execution-profile-v2-drift-to-resolution.md)

---

## 1. Goal

Turn `market_tags` from a classification input into an analytical surface. Answer:

1. **Which tags win more often?** Per-tag resolve-side distribution across all markets.
2. **Which tags have exploitable priced-in bias?** Per-tag entry-price vs resolved-price gap.
3. **Does a given wallet win on some tags but not others?** Wallet × tag realized-PnL attribution.
4. **Does the same tag fit different mechanism types?** Tag × archetype co-occurrence.

None of this requires new data sources — all derivable from `market_tags`, `market_outcomes`, `market_metadata`, plus wallet activity tables.

## 2. Non-goals

- Not building a tag-hierarchy. Tags stay flat opaque strings per spec §3.1 of the migration.
- Not prescribing copy-strategy rules. Analytics inform review; strategy logic reads them but decides on its own.
- Not attempting to classify tag "quality" beyond what the data shows (no hand-written tag→edge maps).

## 3. Analytical primitives

### 3.1 `tag_market_stats` — per-tag resolve distribution

One row per distinct tag:

| Column | Source |
|--------|--------|
| `tag` | market_tags.tag |
| `n_markets` | COUNT(DISTINCT condition_id) tagged with this slug |
| `n_resolved` | markets that appear in market_outcomes |
| `resolved_yes_count` | count of rows where outcome-native resolved_price > 0.97 on the dominant side |
| `resolved_no_count` | complement |
| `yes_share` | resolved_yes_count / (resolved_yes + resolved_no) |
| `avg_resolved_price_yes_side` | mean resolved_price on the YES-side outcome |
| `median_market_volume_24h` | from market_metadata |
| `distinct_co_occurring_tags_top5` | top-5 tags that appear alongside this one |

**Output path:** `data/tag_market_stats.json` or a new SQLite view `tag_market_stats`.

Answers "does this tag resolve YES more often than chance" + "is this tag liquid enough to be tradable".

### 3.2 `tag_wallet_pnl` — wallet × tag realized-PnL matrix

Per (wallet, tag) pair where the wallet has ≥ N resolved positions on that tag:

| Column | Source |
|--------|--------|
| `wallet` | followed/watchlist wallet |
| `tag` | gamma slug |
| `n_positions` | resolved positions tagged with this slug |
| `realized_pnl` | Σ realized_pnl from `_resolved_position_summaries` over matching conditions |
| `win_rate` | positions with realized_pnl > 0 / n_positions |
| `avg_hold_days` | (resolve_ts - entry_ts) median/mean per position |
| `conviction_concentration` | fraction of the wallet's realized absolute-PnL carried by this tag |

Answers "copy their politics fills, skip their sports fills" quantitatively. Requires ≥ 3 resolved positions to report (below that is noise).

### 3.3 `tag_archetype_fit` — tag × classification co-occurrence

Given the new `classification` field with `primary_tag`:

| Column |
|--------|
| `primary_tag` |
| `classification_archetype` |
| `n_wallets` |
| `median_realized_pnl` (across wallets with this primary_tag + archetype pair) |

Answers "which tags cluster with which archetype" and "which tag/archetype combos actually pay".

### 3.4 `tag_drift_profile` — per-tag drift-to-resolution (v2 exec-profile join)

Blocked on v2 execution profile implementation (spec §12). Preview shape:

| Column |
|--------|
| `tag` |
| `n_fills_with_drift_to_resolution` |
| `mean_drift_to_resolution` |
| `win_share_drift_positive` |

Answers "which tags have exploitable entry-price-to-resolution drift (i.e. edge available)".

## 4. Schema & persistence

Option A (chosen): **computed-from-primary** views generated by a script, stored as JSON artifacts in `data/tag_stats/`. Cheap to recompute (all SQL over existing tables). No new write path. Re-running the script idempotently refreshes the artifacts.

Option B (rejected): materialized view in SQLite. Faster reads, but adds a schema and a refresh job, and freshness becomes a correctness concern.

## 5. Implementation surface

1. `scripts/tag_analytics.py` — single CLI producing all four stats artifacts. Stateless. Takes `--out-dir` and `--min-sample` flags.
2. `sniper/analysis/tag_analytics.py` — pure functions for each stat (testable without I/O).
3. Tests under `tests/test_tag_analytics.py` covering:
   - Each helper on synthetic fixtures (known resolve distribution → expected yes_share)
   - Wallet × tag aggregation over a synthetic resolved activity set
   - Tag × archetype co-occurrence when primary_tag is populated
4. JSON artifacts committed periodically (or ignored — cheap to regenerate)

## 6. Opaque-tag discipline

Every function in this spec treats tags as opaque. No hardcoded slugs anywhere in the analytics code. Per-tag stats are keyed on whatever tags appear in the data. Consumer code iterates `tag_stats.items()` and never equality-checks a slug value.

## 7. Consumer integration (explicit)

- **Wallet knowledge pages** can surface `tag_wallet_pnl[wallet]` top rows as "best-performing tags" and "worst-performing tags" without the code assuming what those tags mean.
- **Copy-strategy filter** (future) can read `tag_wallet_pnl` to gate copy at the (wallet, tag) level rather than all-or-nothing.
- **Layer 3 `market_selection_edge`** can cross-reference pooled `tag_market_stats` vs the wallet's per-tag win-rates to detect genuine selection skill.

## 8. What this does NOT claim

- Does not claim a tag's historical yes_share predicts future yes_share (survivorship, regime shifts).
- Does not claim wallet × tag edge is causal (could be accidental concentration).
- Does not claim tag co-occurrence implies semantic relationship.

All outputs are stats over observed data. Interpretation is a downstream decision.

## 9. Rollout

Blocked on nothing — market_tags is populated (Stage 1), wallet activity is in place, market_outcomes has 1896 rows.

Phase 1: `tag_market_stats` (cheapest — no wallet join) → inspect on real data → decide whether the signal merits productionisation.

Phase 2: `tag_wallet_pnl` — one-pass aggregation, tests against known-wallet PnL totals.

Phase 3: `tag_archetype_fit` — requires Stage 4 cutover shipped (✓) so `classification.primary_tag` is populated.

Phase 4: `tag_drift_profile` — blocked on v2 exec profile.

## 10. Open questions

1. How do we handle `unclassified` markets in the aggregates? Report them as a separate row with `tag="(unclassified)"`, or exclude. Recommend include-with-label so the size of the unclassified pool is visible.
2. Tag co-occurrence — should we surface pairs, triples, or only pairs? Recommend pairs only initially; triples get combinatorially noisy at Polymarket's 100+ distinct tags per wallet.
3. Temporal windowing — report lifetime stats or rolling 30d/90d? Recommend lifetime now, rolling later (adds freshness concern).

## 11. Bottom line

Four stats, all computable from existing tables. No new infra. Opaque-tag principle preserved. Produces the "tags that win more often" + "tags that fit X wallet type" signals with zero hardcoded taxonomy. Phase 1 can start immediately.
