# Complete Shyft / Yellowstone Solana migration

Status: proposed; documentation only. Requested by the operator on 2026-10-11. No deployment, provider purchase, credential change or funded transaction is authorized by this planning turn.

## Goal and meaning of complete

The target is confirmed successful acquisition in the source slot for currently authorized native lanes, with routed/confirmed-only and graduation cases graded separately. Provider replacement alone does not satisfy this execution goal. All active Sniper-owned Solana infrastructure uses Shyft: wallet detection, confirmed signer/payment receipts, account/price streams, execution observation, historical/proof reads, funded reads and RPC submission, TPU slot/leader discovery, and active background workers. Yellowstone supplies processed/confirmed transactions, accounts and slots; Shyft HTTP RPC supplies requests and submission. Direct TPU QUIC remains a local validator transport, with Shyft metadata; it does not inherit Shyft's staked connections.

Jupiter route quotes/builds, DexScreener display data, Fomo/J7 external data and other chains remain their existing services. In final Shyft mode, Yellowstone owns automatic Solana buy/sell triggers. External hints remain display/route-hint data; the existing verified Jupiter backup route remains available through confirmed Yellowstone proof under its unchanged ownership and admission gates. Existing positions still receive source sells through the Yellowstone confirmed watcher. External display feeds may continue. This does not change wallet arming, venue ownership, gates, sizing, premium floors or exit policy. No new trading authority. Use subscription-included RabbitStream for bounded unsigned preparation when entitled; no custom raw-shred decoder, signer rewrite or Rust feed rewrite.

Complete means no active Helius/public Solana RPC or third-party Sender/Nozomi submission attempt, including maintenance/research workers. Historical files and rollback support may retain old provider names. EVM transport is unchanged. The requested final provider set explicitly supersedes Solana's old public-fallback policy; amend the precise current policy documents during implementation. Do not silently keep public RPC because an old comment requires it.

## Invariants and failure behavior

- No new synchronous provider request, lock, retry, database write or protobuf compilation on funded entry. Receipt callbacks run before measurement publication. Retain bounded metadata queues and one-owner dispatch.
- Preserve 500 ms original receipt/resume window, TPU 1000 ms frozen-clock and two-slot guard. Replay/reconnect/confirmed completion never reset the first receipt time.
- Processed native program initiation remains eligible only under existing program-specific rules. Processed balance deltas alone never become confirmed signer/payment proof. Successful CONFIRMED stream and exact bound full metadata may satisfy existing proof validation. Missing metadata is unknown.
- All sent bytes and signatures preserve the existing write-ahead identity, four-state transport results, ambiguous-send recovery, full-close claims and atomic fill accounting. A timeout, HTTP 429, reconnect or null read never proves a transaction failed.
- Keep current WRITE rotation semantics: only explicit safe pre-admission JSON-RPC rejection already supported by the pool allows automatic rotation; HTTP/transport ambiguity does not. Do not broaden rejection classification to Shyft errors without a documented guarantee and regression witness. READ allowlist behavior remains intact.
- Atomics stay integer/decimal TEXT; versioned lookup keys, Token-2022, cashback, WSOL unwrap, fee siblings, refunds, instruction order and duplicates retain exact identity checks. KRAW/Santaro repaired receipts are compatibility fixtures.
- No shared env/module monkeypatch or thread-shared resolver swap. Pass endpoint/config explicitly; legacy aliases are read once at startup only in legacy mode.
- Credentials never appear in logs, argv, artifacts or UI. Fingerprints are labels only; different API keys do not prove quota isolation. Record provider account/project allocation and limits without keys.
- Missing account update, stream timeout, overflow, partial roster acknowledgement, rejected filter and provider outage record typed unknown coverage. Retain last good marks only within their existing freshness limits. Observer unavailability cannot veto funded entries.
- Rollback restores previous environment, manifests, pinned runner/web/worker roots and exact old provider settings; unresolved signed transactions reconcile first. Do not release claims or replay old buys. No backup unless separately requested.

## Same-slot contract and the actual delays

`head_at_recv_minus_s = head_at_recv - source_slot`; negative values mean a transaction beat the feed's own slot notification. This is an arrival/head-skew measurement, not knowledge of a future buy. Keep head age, connection generation, feed, raw source slot and local monotonic times. A stale/missing head is unknown. Do not convert -1 into 400 ms of remaining slot time or disable the TPU freshness guard. Slot duration and bank-close times vary; no fixed slot-length promise.

Confirmed same-slot fill requires successful chain receipt, exact our signature/source-event join, real positive acquired atomic quantity and `landing_slot == source_slot`. A failed transaction landing in S, dispatch during S or RPC/TPU ACK is not a fill. Confirmed receipt slot/identity/quantity grading does not require a processed observer or matching process boot; those are separate prerequisites for a <=200 ms interval bound. A missed observer can censor milliseconds without erasing a valid S+0 receipt. Finalized/fork reconciliation may later censor a provisional confirmed result. Record independent admission cohort counts: S+0, S+1, S+2+, signed failures, refusals, no submission, unresolved and missing observation. The primary denominator is every unique successful armed-wallet source buy in the frozen, currently funded-chain/venue cohort, independent of our cache or builder success; report ordinary gate refusals as separate outcomes, not remove them after the fact. Also report submitted-only and warm-hit rates as secondary diagnostics.

Separate strata before reading our outcomes: (a) locally provable processed native Pump/PumpSwap paths, (b) routed paths requiring confirmed signer/payment/acquisition, (c) graduation/new-pool creation, and (d) existing ordinary fallback. For routed transactions, the confirmed-proof requirement can consume the source slot; earlier intent only overlaps preparation. When proof or pool availability arrives after S, label the constraint and target earliest permitted landing, not fabricate same-slot feasibility or bypass proof.

Existing receipt evidence: Chada local signing 0.161878 ms, QLI 0.151551 ms, ALT 0.176403 ms. Chada/QLI proof wait 40.988/50.578 ms and receipt-to-dispatch 56.915/62.166 ms, yet both landed S+2. KRAW's fallback market stage 348.144 ms (343.835 ms probe) and broad signing stage 139.355 ms include reads/building; they are not comparable cryptographic-sign timings. These are exact incidents, not population p50/p90. Retain existing native solders signing and existing watcher-to-runner wake bridge.

Engineer target for admitted, ready native lanes: authority-ready to first dispatch p50 <=10 ms / p90 <=25 ms, local signature p90 <=1 ms, zero new provider calls on the ready path. Measure required reservation/write-ahead identity commits inside the budget; keep them durable. Routed proof-ready to dispatch uses the same local budget; report proof waiting separately. Miss/stale/unknown inputs retain ordinary gates and coverage; never add a new speed-based admission veto or skip a check to meet the target. These are targets to validate, not measured promises or millisecond refusal thresholds.

Use current LanePrefetcher, builder pool caches and WarmExoticLegs. Preload/stream validated mint decimals/token program, ATA identity/existence, venue/pool/fee/config state, compute class, supported lookup tables, blockhash/expiry, balance/funding snapshots and quote legs off entry. Share existing data carefully: source route metadata does not prove our custody balance or an absent ATA, and source transaction ALTs do not prove a Jupiter route's different lookup table. Dynamic price/reserve/LP and source average checks remain current and bound to the exact event/pool. Admission/reservation/book availability and signed minimum output remain authoritative at send; cache data, never cache permission to spend.

RabbitStream is transaction-only early input without logs/balances/errors. Existing metadata-required native decoder cannot consume it directly. Add a separate intent-preparation adapter that verifies structural signature/owner/program/account/lookup identity and schedules bounded preparation; it cannot reserve, sign, send, assert source payment/acquisition or establish confirmed proof. Join with exact authoritative Yellowstone `(signature, owner, slot)` and pool/mint/clip/config identity. Keep intent arrival and authoritative receipt times distinct; the preparation clock cannot extend or reset the existing 500 ms execution clock. Later failed/dead/incompatible metadata discards prepared work. Yellowstone remains the slot/account/proof owner.
